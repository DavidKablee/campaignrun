# C42 — a name is enough to start, and an email is what makes it an account
Status: done      Depends on: C37, C41
## Goal
Two ways in, both honest. An email account that confirms the address by link, and an account made
from a board name alone for a player who will not hand over an address to a game they have not
played yet. Because a name-only account cannot be presented by a second device, the game asks for
an email later — on a ladder, not every run.
## Done when
A name-only account survives losing its session cookie, its runs are saved and stay off the public
boards, attaching an email turns it into an ordinary account that can sign in anywhere, and the
prompt that asks for one can be deferred and comes back.

## Shipped

### What "just a name" actually is
A real server account with `email`, `password_hash` and `password_salt` null, and one credential:
a random 32-byte **device key**, stored hashed in `device_keys` and held in that device's
`localStorage`. `POST /api/auth/guest` creates both and returns the key once. `POST /api/auth/device`
trades it for a session when the 30-day cookie lapses, which is what a returning player hits —
there is no login for an account with no password.

That shape is the answer to "why would I ever add an email", and it is why the key is device-local
rather than something prettier: **a name is not a credential.** Anyone can type `namer82564`. If a
name alone could reach the account from a new device, the account would belong to whoever typed the
name first. So the UI says the two consequences plainly instead of discovering them for the player
later: clearing site data ends the account, and it cannot be opened anywhere else.

The device key is the one secret in the game that page JavaScript can read — the session stays an
httpOnly cookie. That is a real downgrade and the reason the prompt exists, so it is stated in
`deviceKey.ts` rather than left for someone to find.

### Name-only accounts cannot reach the public boards
Nothing new was needed: C41 made every public surface count confirmed addresses only, and a
name-only account has no address. That is the right answer rather than a convenient one. These
accounts cost one POST each, and what the 200-player privacy floor withholds is other people's
Contender choices — a floor that a script can clear for the price of a loop is not a floor.

So the split is: play, personal bests and the local board need nothing; the public board and the
live map need a confirmed address. Saying so is also the most persuasive line in the prompt.

### Attaching an email
`POST /api/auth/email/attach` takes an address **and** a password together, because an address with
no password is still not something a second device can sign in with, which is the only thing the
player is being asked for. It refuses when the account already has an address (`has-email`, 409):
changing an address has to prove control of the old one, and this route asks for no password, so
allowing an overwrite would make a stolen session enough to take an account over. The new address
starts unverified like any other, and the usual link is mailed.

### Asking, on a ladder
`emailPromptDue()` on the client decides whether to ask: never for an account with an address, not
until the player has `emailPromptAfterRuns` runs banked on the server, and not during a snooze.
`snoozeUntil()` on the server decides how long "not now" lasts — 24 hours, then 3 days, then a week,
with the last rung repeating.

A permanent "never" is deliberately not offered. The ask is the only route to a second device, so a
"never" would quietly promise a saved campaign that the account cannot keep. Nagging every run is
the other way to get this wrong, and the ladder is what sits between the two. The counter lives in
the database, not in device storage, so it cannot be reset by clearing site data — and so the
decision is testable without a browser.

The ask appears on the result screen, which is the moment the player has just made something worth
keeping, and permanently in Account.

### Nullable columns, and the routes that had assumed otherwise
`users.email`, `password_hash` and `password_salt` became nullable, so four routes needed an answer
for an account that has none: `verify/request` returns `no-email`, `password/change` returns
`no-password`, login handles a null hash (unreachable — a name-only account has no address to look
up — but handled rather than assumed), and Account hides the Sign out button for a name-only
account, because there is nothing to sign back in with and the button would read as "leave" while
acting as "lock myself out".

The seven routes that answer with a user object now go through one `userPayload()`. Three of them
had their own copy of the shape, which is how a name-only account would have come back looking like
a full one on exactly one code path.

## Tests
`api/test/api.test.ts` + 15: creating an account from a name, the shared username namespace, the
device-key exchange, an unknown key, the key dying with the account, runs saved but withheld from
the board, `no-password`/`no-email`, attaching (including the login that then works, the board row
that then appears, a taken address, an overwrite attempt, a short password), and the snooze ladder.

`api/test/emailPrompt.test.ts` (4) covers the ladder itself, including a nonsense dismissal count —
an `Invalid Date` there would store a null and ask again immediately.

`apps/game/test/emailPrompt.test.ts` (7) and `apps/game/test/deviceKey.test.ts` (6) cover the client
halves. The storage tests include both private-mode failures: the kind that throws, and the quieter
kind that accepts a write and keeps nothing. Both mean the account is unreachable on the next boot,
so `continueAsName` treats them as a failure before the account is created rather than letting the
player discover it a week later.

233 tests (was 202).

## Open
- **No mail provider still.** Attaching an email mails a confirmation link through the same
  `Mailer` that has no implementation, so on a real deployment that link goes nowhere. C41's boot
  refusal covers it, but it now blocks a second flow, not one.
- Changing an address on an account that already has one is still not possible. It needs a
  confirm-at-both-addresses flow; `has-email` is the placeholder.
- A device key never rotates and is never listable, so "sign out my other phone" does not exist for
  a name-only account. It cannot meaningfully exist until there *is* another device, which is what
  attaching an email is for.
- Nothing merges two accounts. If a player makes a name-only account on a phone and a full account
  on a laptop, they are two accounts and the game does not say so.
