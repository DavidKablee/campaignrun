# C37 — Accounts, an API and a database
Status: done (not deployed)      Depends on: C11 (consent), C35 (parties)
## Goal
Scores lived on the device. Put them on a server so a player's board follows them, and so the
campaign map can be built from real play instead of generated numbers.
## Done when
`pnpm verify` green without a database; the full suite green against a real Postgres; a player can
sign up, post a run and see it on a public board; a Contender id never reaches the database without
consent.
## Shipped
### The API — `api/`
Hono on Node, Postgres through `pg`, bundled with esbuild (`pnpm --filter @cr/api build`) because
the deploy artefact should be one file and because `@cr/content` uses extensionless imports that
bare Node will not resolve.

| Route | Does |
|---|---|
| `POST /api/auth/signup` · `login` · `logout` | email + password, session in an httpOnly cookie |
| `GET /api/auth/me` | who the cookie belongs to |
| `POST /api/auth/consent` | the C11 Contender-sharing switch |
| `POST /api/scores` · `GET /api/scores/mine` | post a run, read personal bests |
| `GET /api/board/:stateId` | public region board, one row per player |
| `GET /api/standings` | per-region party tallies, above the privacy floor |
| `GET /api/account/export` · `DELETE /api/account` | take your data out, or take it away |

Passwords use `scrypt` from `node:crypto` — memory-hard, ships with the runtime, one less native
build in the deploy. Session tokens are random 32 bytes; **only a SHA-256 hash is stored**, so the
sessions table is not a list of working credentials. Login compares a real hash whether or not the
address exists and answers identically either way, so the response does not disclose who has an
account.

### Guardrail 10 is enforced in the database, not just the client
`scores.contender_id` is nullable and the server writes it **only** for an account that has
consented — it drops the field on a post from anyone else, even if the client sends it. Withdrawing
consent runs `update scores set contender_id = null` for that user, so the choice is honoured
backwards as well as forwards. Tests cover all three paths.

### The privacy floor
A region's party breakdown is built from Contender choices. With a handful of players an aggregate
is not an aggregate — it names them. So `/api/standings` publishes a region's tallies only above
`CR_MIN_PLAYERS` (default 200, matching the number guardrail 2 already uses for polling-style
figures), and below it sends **no tallies at all** — not zeroes, not a leader. The client keeps the
generated practice numbers for that region and says so on screen.

### The client
`apps/game/src/api/client.ts` (fetch wrapper), `onlineStore.ts` (session + server bests, not
persisted — the cookie is the session and a local copy would only go stale), `liveBoard.ts`
(`mergeStandings`, pure and tested), and `ui/AuthScreen.tsx`. The map now shows `Live · n` and
labels every region with where its numbers came from. A finished run posts to the server when
signed in.
## Tests (170 with a database, 137 without)
- 16 unit tests with no database: password verify/salt/malformed-hash, token hashing and
  uniqueness, payload validation against the real content ids, and the privacy floor against a
  fake `Db`.
- 17 integration tests against real Postgres (`DATABASE_URL` set, skipped otherwise): duplicate
  email and case-insensitivity, httpOnly cookie, login disclosure, session invalidation on logout,
  the three consent paths, board ranking one row per player, the floor withholding a breakdown,
  export, and a delete that leaves zero rows in all three tables.
- 7 client tests for `mergeStandings`.
## Open
- **Not deployed.** It has only run against a throwaway local Postgres. Hosting, a managed
  database, TLS, backups and a real `CR_ALLOWED_ORIGINS` are all still to do.
- **No email verification and no password reset.** Both are table stakes for email sign-in and
  neither exists yet. A player who forgets their password currently has no way back in.
- **No rate limiting.** Signup, login and score posting are all unthrottled. Login especially needs
  it before this is public.
- **No server-side replay verification.** A posted Crowd is bounds-checked but otherwise trusted;
  that is C12's job and it is still open.
- **Local storage is still the signed-out path.** Scores go to the server when signed in, and stay
  on the device otherwise, which is also what keeps the PWA working offline. Removing local play
  entirely is a product decision, not a technical one.
- **The legal review is now load-bearing.** Holding email addresses and passwords moves the
  privacy/terms review from "before public launch" to "before this server is reachable by anyone".
