# C41 — the things that are not optional if accounts ship
Status: done      Depends on: C37
## Goal
Close the six gaps that made the C37 account layer unsafe to put in front of the public: no rate
limiting, no password reset, no email verification, unverified scores, an unclamped board query,
and `console.error` as the whole of observability.
## Done when
Every one of them is enforced by a test that runs against a real Postgres, and the flows a player
actually touches — confirm an address, recover a password — work end to end in a browser.

## Shipped

### Rate limiting
Two layers, because they fail differently.

`rateLimit.ts` is a fixed-window counter in process memory, keyed on client address, on signup,
login, forgot, reset, verify and change. It is per-instance and clears on restart, which is said
out loud in the file: it stops a script hammering one endpoint and nothing more. `x-forwarded-for`
is only read when `CR_TRUST_PROXY=true`, since anyone can send that header and trusting it by
default would let one attacker present a fresh address per request.

The second layer is in the database, keyed on the **address being attacked** rather than the
address attacking it: `login_throttle` counts failures and locks for `lockoutMinutes`, surviving
restarts and IP rotation. Unknown addresses are counted too — a lockout that only happened to real
accounts would itself be an account-existence oracle. A correct password does not open a locked
account; a password reset does, which is the path a real player has.

Score posting is capped per account rather than per address, since the session is the thing being
spent.

### Password reset and email verification
`email_tokens` holds both kinds. The raw token only ever exists in the email — the row stores its
SHA-256, the same treatment as a session token, so a database dump does not hand over working
links. Spending one is a single `update … where used_at is null and expires_at > now() returning`,
so two requests racing the same link cannot both win. Asking for a second link invalidates the
first.

A reset **destroys every session on the account**. Someone resets a password when they think
another person is on the account, so leaving that person's session alive would defeat it. The same
goes for a deliberate change, which is in Account with the current password required.

`/api/auth/password/forgot` returns the same 202 for an address that exists and one that does not,
and the client says the same thing back — a kinder "no such account" would undo the server's work.

**Verification has teeth:** public boards and live standings count confirmed addresses only. Without
that the privacy floor in `standings.ts` is a formality, because 200 signups is an afternoon of
scripting and clearing the floor is exactly what publishes other people's Contender choices. Play
is not gated; only the public surface is.

There is no mail provider — that needs an account only the project owner can create — so `mailer.ts`
is an interface with a console implementation, and **the API refuses to boot in production without
one**. The quiet version of this failure looks healthy from outside while every locked-out player
stays locked out. `CR_ALLOW_NO_MAIL=true` overrides it for staging, loudly.

### Scores the game could actually produce
`isPlausibleRun` moved from `apps/game/src` to `@cr/sim` and now runs on the server, where it
matters: until now the zod ranges were the only thing between a curl command and the top of a
public board. Capacity is taken from the ride in content, not from the request — otherwise
`capacity: 200` simply buys a proportionally larger lie.

**Turning it on exposed a bug in the check itself.** Its crowd ceiling knew about momentum, Full
House and On Beat — it was written in C09, before C28 and C30 added the PVC buff, the Rally
Saturday window and the signature-ride bonus, which are another 2.4x between them. Enforcing the
stale bound would have rejected real Rally Saturday runs with a 422. `maxCrowdFor()` now composes
every multiplier `deliverCrowd` applies, plus a flat allowance for rival outpacing bounded by how
many entities fit on the course at the tightest legal spacing. `signatureRideBonusPermille` moved
out of an inline `1100` in `App.tsx` into `sim.json`, where the bound can read it.

This is an absurdity filter, not proof. It rejects a claim the simulation could not have produced;
it does not catch a plausible claim that was never played. That still needs server-side replay,
owed from C12.

### The rest
- `/api/board/:stateId?limit=` is clamped to 1…`limits.board.maxRows`. `Number.isFinite` let `1e9`
  through to a clamp that lived one call deeper, where nothing said it had to stay.
- Cookie scope is configurable and **checked at boot**: `CR_COOKIE_SAMESITE=None` without a secure
  cookie now throws instead of being discovered in support.
- One JSON line per request with a request id, echoed in `x-request-id` and returned in a 500 body
  so a player can quote it. Nothing logs an address, a password, a token or a Contender id.

### Numbers
All of them live in `packages/content/data/limits.json` with `CR_*` overrides, because the client
quotes them to the player ("try again in 15 minutes", "this link lasts 60 minutes") and a second
copy drifts.

## Client
A route nobody can reach is not a fix, so: a *Forgot your password?* path on sign-in, a one-job
reset form the link lands on, an unconfirmed banner in Account with a resend, and a change-password
form. `authLink.ts` reads the token from the query **and strips it from the address bar** — a reset
token is a credential for an hour, and a URL ends up in history and in the `Referer` of anything
the page loads.

## Verification
- `pnpm verify` green; `DATABASE_URL=… pnpm test` → **202 tests** (was 179). 36 of those are API
  tests that had never run in CI at all.
- CI now starts a Postgres service and runs the e2e suite, so both stop being green-by-skipping.
- Live loop in Chrome against the real API: sign up → unconfirmed banner → follow the mailed link →
  `emailVerified: true` and the banner gone → sign out → forgot → follow the reset link → new
  password set → old password 401, new password 200, and no token left in the URL.

## Open
- **No mail provider.** Everything around it is real; `send()` is a stub and production will not
  boot without it.
- The IP limiter is per-process. Two instances behind a load balancer each allow the full budget —
  move it to Redis or Postgres if this ever scales horizontally. The per-address lockout already
  survives that.
- No CAPTCHA or proof-of-work on signup, so the limits are the only thing between a botnet and a
  pile of accounts. Verification keeps those accounts off the boards, which is the part that
  matters most.
- Sessions are never rotated on privilege change beyond password reset/change, and there is no
  "sign out everywhere" button of its own.
- Still no server-side replay verification: the plausibility bound is a floor, not proof.
- `email_tokens` and `sessions` accumulate expired rows; `purgeExpiredSessions` exists but nothing
  schedules it, and there is no equivalent for tokens.
